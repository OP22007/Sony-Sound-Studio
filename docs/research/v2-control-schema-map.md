# MDR V2 control schema evidence map

This map records app-side schemas found by static inspection of the shipped APK (SHA-256 `58837826f5f145cd0ad9689a298d2bfe9702f4d51d6d4e67d41440175ec0892c`). The APK was not executed. Static serializers and validators show protocol capability, not XM6 runtime support. The full machine-readable notes and evidence IDs are in [v2-control-schema-map.json](v2-control-schema-map.json); evidence records remain private in `.research/evidence/readout-and-control-research.json`.

## Findings

- **Function support response:** `CONNECT_GET_SUPPORT_FUNCTION` request bytes are `06 00`. The response parser reads `[07 00 count (functionType version)*count]`, requires exact length `3 + 2*count`, and treats the pair version as unsigned. It drops `NO_USE` entries. REA confirms `fromByteCode(table, byte)` compares both table and byte. REA could not disassemble the large enum initializer, so selected values were decoded from the exact APK DEX static initializer: table NO_1 `CUSTOM_EQ=0x55`, `CUSTOMIZABLE_SOUND_EFFECT=0x59`, `AMBIENT_SOUND_MODE_ONOFF=0x66`, `AMBIENT_SOUND_MODE_LEVEL_ADJUSTMENT=0x67`, `AMBIENT_SOUND_CONTROL_MODE_SELECT=0x69`, and `AUTO_NCASM=0x70`. These are app enum declarations, not headset capability results.
- **NC/ASM inquiry requests:** static command IDs are capability `0x60`, status get `0x62`, status set `0x64`, parameter get `0x66`, parameter set `0x68`. Captured get factories append the inquiry byte after the command header. Inquiry enum byte/name pairs are listed in the JSON map.
- **NC/ASM parameter inquiry `0x17`:** the GET request is `[0x66, 0x17]`. Its 7-byte response is `[0x67, 0x17, …, NcAsmMode, AmbientSoundMode, ambientLevelByte]`, with the two mode fields at offsets 4 and 5 and the unsigned level byte at offset 6. The SET serializer emits `[0x68, 0x17, ValueChangeStatus, NcAsmOnOffValue, NcAsmMode, AmbientSoundMode, ambientLevelByte]` (7 bytes). The observed enum values are `UNDER_CHANGING=0`, `CHANGED=1`; on/off is `0/1`; NC/ASM mode is `0/1`; ambient mode is `NORMAL=0` / `VOICE=1`. The serializer truncates an integer to its low byte; the parser does not validate a semantic ambient-level range. The app maps the slider using capability-provided min/max/step. Fixed XM6 3.1.5 limits require device capability readback; static APK evidence does not establish that the headset advertises this inquiry or accepts/applies a SET.
- **EQ/EBB:** this APK calls the protocol family EQEBB. Its command IDs include capability get/response `0x50/0x51`, status get/response `0x52/0x53`, parameter get/response `0x56/0x57`, and parameter set `0x58`. Inspected capability, status, and parameter GET factories append an inquiry byte, and their request validators require exactly two bytes and a recognized inquiry. `CUSTOM_EQ` is inquiry `0x31`; the remaining inquiry IDs are in the JSON map. The status request parser is verified, while response field layouts and validators remain unresolved.
- **NC/ASM capability and status requests:** the APK exposes GET requests `[0x60, 0x17]` and `[0x62, 0x17]`, respectively. A live read-only XM6 probe returned capability bytes `61 17 02 00 01 14 01 01 01 14 01` and status bytes `63 17 00`. These exact bytes are observations only; the capability fields and status-response byte meaning have not been independently decoded. The endpoint's header-matching capability reply alone does not prove that inquiry `0x17` is supported or that its parameter response reflects active NC state. The high-level caller's requirement for these inquiries before a parameter SET remains unresolved.
- **SETs:** the NC/ASM `0x17` SET wire layout is known. The automatic timeout-triggered rollback was removed. The app now refuses to confirm NC mode while the parameter response status is `UNDER_CHANGING`, and sends an explicit user-selected Off request even if the last decoded mode was already Off. Latest diagnostics report baseline and latest parameter bytes `67 17 00 00 00 00 00`; under the captured enum mapping, byte 2 is `UNDER_CHANGING`, so this is not a final Off readback. The user explicitly reports ANC stays ON in the latest check, but audible observation is not protocol confirmation. Final runtime readback and notification behavior remain under investigation; stable mode application is unresolved. Other NC/ASM setter branches remain unresolved. EQ wire response layouts are partially established and one XM6 band now has a hardware-confirmed SET/restore result; other bands and models are unverified.

## Live hardware update — 2026-11-01

On the user's WH-1000XM6 with firmware 3.1.5, diagnostic baseline and latest NC/ASM parameter reads both returned `67 17 00 00 00 00 00`. Under the captured original-app schema, byte 2 is `ValueChangeStatus`; zero means `UNDER_CHANGING`. Thus these reads are not a final Off state even though the next byte is zero. The user explicitly reports ANC remains ON in the latest check. This is an audible user observation, not protocol confirmation; final runtime readback is unresolved.

The automatic timeout-triggered rollback has been removed. The app now refuses to confirm a mode while status is `UNDER_CHANGING` and sends an explicit user-selected Off request even if the last decoded mode was already Off. Notification behavior is under investigation. A read-only capability/status probe returned capability bytes `61 17 02 00 01 14 01 01 01 14 01` and status bytes `63 17 00`; these are raw observations only. The generic capability response validator checks header and minimum length, and the typed decoder body for inquiry `0x17` is not present in saved evidence. A header-matching response therefore does not prove the feature is supported. The status response layout and byte meaning are also unresolved. A control-service reconnect also timed out in Windows with code `10060`.

The original app's serializer evidence confirms the SET byte order and enum mapping, but does not establish whether the capability/status handshake is mandatory, explain the status GET response, or prove the mode was applied.

Ambient-level writes remain unavailable because the XM6 capability response and supported min/max/step have not been established. In a separate XM6 3.1.5 test, the live UI changed the 500 Hz EQ step from 5 to 6 and a subsequent device readback confirmed it; restoring 5 was also confirmed. This validates one band's SET/readback/restore path only. Other EQ bands, preset behavior and other models remain unverified. Static SET fields and a transport ACK alone are not evidence that a feature is applied.

## Evidence boundary

These are static companion-app observations only. Runtime support requires the actual device's capability response; successful control requires additional device observations. The hardware-verified identity, firmware and battery results elsewhere in the readout spec do not verify control features.
