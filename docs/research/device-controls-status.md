# Device control implementation status

Status: 2026-11-01. The app keeps each control unavailable until the connected device advertises its function, returns a valid current value, and the control's native request path can confirm a new value.

## Sound enhancement (DSEE)

The Android APK exposes the audio `UPSCALING_AUTO_OFF` parameter as a three-byte value: `0=OFF`, `1=AUTO`. Its GET/RET/SET/NTFY commands are `0xE6/0xE7/0xE8/0xE9`; the inquiry is `0x01`. GET reply and notification validators require exactly three bytes, the matching inquiry and a recognized value. The setter serializer emits command, inquiry and enum in that order. The desktop implementation requires a successful support-function reply advertising table-1 function `0xE2`, then reads `[E7,01,value]`; it sends `[E8,01,value]` and considers the change complete only after a matching GET readback. Final `0xE9` notifications update confirmed state.

## Automatic power off

The APK's DEX enum constructor maps `AUTO_POWER_OFF` to table NO_1 function `0x24` and `AUTO_POWER_OFF_WITH_WEARING_DETECTION` to NO_1 function `0x25`. The user's WH-1000XM6 support-function capture contains `0x25` and does not contain `0x24`. These are distinct functions; the standard setter must not be sent through the wearing-aware function.

For standard inquiry `0x04`, the APK capability reply is `[0x21,0x04,count,option...]`, parameter GET is `[0x26,0x04]` with exact reply `[0x27,0x04,activeOption,selectedTime]`, and SET is `[0x28,0x04,activeOption,selectedTime]`. Both parameter bytes must be values in the decoded capability list. The option enums are 5, 15, 30, 60, and 180 minutes plus disabled. The desktop now exposes the standard mode and timer only when function `0x24`, the capability list, and the current parameter GET all validate; it requires matched readback and verifies restoration after a failed change.

For XM6's advertised function `0x25`, the desktop performs only GET_CAP inquiry `0x05` and GET_PARAM inquiry `0x05`, records the bounded raw replies, and exposes the current value read-only when both parse. The enum includes “when removed from ears” and “disabled” as well as the timer values, but a distinct verified SET/readback route for this variant is not established. The raw support-function value `0x25` belongs to the function enum here; a command byte with the same numeric value belongs to a different enum and is not evidence of feature support by itself.

## XM6 advertised controls without validated setters

The shipped APK's `FunctionType` DEX values decode the user's complete XM6 support reply as follows: `NO_1/0xF1` is `PLAYBACK_CONTROL_BY_WEARING_REMOVING_HEADPHONE_ON_OFF`; `NO_2/0x41`, `0x42`, and `0x44` are voice-guidance language/volume variants. The XM6 advertises those functions. The desktop now labels Wear and Voice Guidance as advertised with their read/write schemas pending. The APK evidence retained for wear detection establishes separate status GET/parser paths (`0xF6/0x01` and `0xF2/0x01`), but it does not establish that either path is the playback-pause preference or provide a validated SET/readback round trip.

The APK's Bluetooth sound-quality function variants map to `NO_1/0xE1` and `NO_1/0xE3`; neither appears in the XM6 support reply, so the desktop marks Bluetooth sound quality not advertised for this connection. The separate touch-panel backlight function maps to `NO_1/0x2F` and is absent, but that function is not equivalent to the touch sensor control-panel setting. Generic notification-tone and multipoint controls remain unvalidated because their support mapping is not specific enough to claim absence from this reply.

## Ambient-level range probe

The desktop now requests the read-only NC/ASM capability reply for inquiry `0x19` on devices that successfully read that inquiry and advertises the bytes in diagnostics. The response layout and mode-specific minimum, maximum, and step are still undecoded, so no slider or ambient-level SET is exposed. A parameter level read remains useful as a current value only; it is not a valid range.

## Focus on Voice

For the WH-1000XM6 firmware 3.1.5 route, the existing validated inquiry `0x19` response exposes `AmbientSoundMode` at offset 5 (`0=NORMAL`, `1=VOICE`). The control reuses the already hardware-confirmed nine-byte inquiry-`0x19` setter, preserves the other fields, and waits for a matching `CHANGED` readback before updating the UI. Final notifications update the displayed value. It appears only when the advertised function set contains `0x69` and the inquiry-`0x19` GET is valid.

The label `Focus on voice` reflects Sony's `VOICE` ambient-sound mode; the wire field is a mode selection, not a standalone Boolean flag. The static schema and the hardware-tested inquiry-`0x19` mode path are documented in [NC/ASM inquiry 0x19 schema](v2-ncasm-19-schema.md). This new control has not yet had a separate hardware SET/readback test.

## Speak-to-Chat Type 2

The desktop exposes a Speak-to-Chat toggle only when the connected device advertises `NO_1/0xFC` and returns a valid Type 2 parameter read. GET/RET are `[F6,0C]` and exact four-byte `[F7,0C,enabled,auxiliary]`; SET is `[F8,0C,enabled,auxiliary]`; NTFY is `[F9,0C,enabled,auxiliary]`. Both bytes use Sony's `OnOffSettingValue` (`0=ON`, `1=OFF`). The UI changes the first byte and preserves the second from the latest device read. A matching GET is required before confirmation. Sony's separate Type 2 status route `[F2,0C] -> [F3,0C,enabled,effectStatus]` is not conflated with this preference toggle; the desktop does not currently display the active effect status.

## Listening mode — capability-driven options

Listening mode is a derived selection across separate device controls. The shipped APK maps `NORMAL`, `BGM_MODE`, and `UPMIX_CINEMA` to separate repositories; Standard clears the active mode, while BGM and Cinema each set their own control. The desktop creates one select from the intersection of advertised capabilities and valid current reads. It offers Standard with BGM when BGM is advertised, and adds Cinema when E5 is also advertised. It withholds the menu when series function EC is advertised because the series path can also select Cinema and its wire schema is not implemented.

BGM uses inquiry `0x03` when function E4 alone is advertised or `0x09` when function EB alone is advertised. If both BGM function IDs are present, the selector is withheld until their selection flag is mapped. GET is `[E6,inquiry]`, and the exact four-byte RET is `[E7,inquiry,OnOffSettingValue,RoomSize]`; SET is `[E8,inquiry,OnOffSettingValue,RoomSize]` and NTFY is `[E9,inquiry,OnOffSettingValue,RoomSize]`. `OnOffSettingValue` is `0=ON/BGM`, `1=OFF/Standard`; `RoomSize` is `0=SMALL`, `1=MIDDLE`, `2=LARGE`. The separate Background Music distance control maps those values to Sony's APK labels: `SMALL=My room`, `MIDDLE=Living room`, `LARGE=Cafe`. This mapping comes from the APK resource values `BGM_Setting_R1/R2/R3`, the `RoomSize` enum initializer, and the BGM listening-option binding map in APK SHA-256 `58837826f5f145cd0ad9689a298d2bfe9702f4d51d6d4e67d41440175ec0892c`. The control appears only after the BGM function and a valid current parameter read are confirmed. Its setter preserves the BGM on/off byte, requires a matching readback of both fields, and verifies the previous distance if a change fails. Enabling or clearing BGM from the listening-mode selector also preserves the chosen room size. Cinema uses E5 and inquiry `0x04`; GET is `[E6,04]`, RET/NTFY are exact three-byte `[E7/E9,04,OnOffSettingValue]`, and SET is `[E8,04,OnOffSettingValue]`; `0=ON/Cinema`, `1=OFF/Standard`. The controller disables the current mode before enabling another, waits for readback of every changed field, and restores the previous pair only when the restored values can be verified. If any supported GET is invalid, the selector stays unavailable. The previously captured XM6 function reply includes EB and E5 (with neither E4 nor EC), so it should expose Standard, Background Music, and Cinema plus the BGM distance selector once valid BGM and Cinema GET replies are read. Hardware SET/readback for listening modes is still pending.

## Ambient sound level bounds

The UI does not expose an ambient-level slider yet. The APK's range API obtains minimum, maximum and step through a value keyed by `AmbientSoundMode`, so the observed inquiry-`0x17` bytes cannot safely be treated as NC/ASM mode ranges or reused for inquiry `0x19`. Inquiry-`0x19` capability response parsing and mode-specific range semantics remain unresolved. No ambient range is hard-coded.
